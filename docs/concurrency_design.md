### Server Concurrency Strategy

- **Architecture Choice:** Multithreading (`threading.Thread`) is the architecture of choice for this project's concurrency management. Threads are, in general, more straightforward than non-blocking socket select, with more precise management of behind-the-scenes processes (e.g. updating game state, validating questions, etc.). A thread in Python is a sequence of instructions that the client and server manage. Multithreading allows for the client and server to handle multiple actions simultaneously, while state is maintained between the two. Importantly, Python multithreading allows the various threads to share code, which, for Headbands, is very practical, as there are only two roles either client may be. It is also harder "block" the server using multithreading, as both threads are separate events and thus do not have to wait for each other unless told specifically to do so. However, sockets will still need to be used to send data as multithreading doesn't provide that capability by itself. Sockets will rely on multithreading processes and locking to organize communication without blocking instead of turning off blocking on the socket itself. The server begins by creating the sockets and listening for clients. Once clients are accepted, threads are created for each client socket (based on game activity and state updates). These threads handle messages and state updates that are received from the server. Once the game is over, the thread is closed then the socket is torn down.

- **Synchronization Logic:** To prevent race conditions and maintain state synchronization, `threading.Lock` (lock condition) will be used to protect access to shared state resources by both clients. The lock condition essentially makes it so whatever client acquires the lock to a certain shared variable will be the only client that can alter that variable until the lock is released. This can be built into method conditions, making it so state variables that require updating and may risk race conditions (e.g. score, guesses, tie-breaker guesses, etc.) can be changed without manually acquiring and releasing the lock variable every single time. Locks will be acquired for updating state (player roles, points) and for tie-breaking guesses in particular because these messages are broadcast messages. The clients aren't expecting to wait for the other client or for the server during these events, so locking must be in place to avoid collisions and data corruption. Tie-breaking guesses in particular will be a sticking point that must be managed with locking because both clients may be sending guesses at the same time to the same location. Locks are released at the end of a state update when new roles are assigned and points are updated, or at the end of sending a guess during a tie-breaking round.
